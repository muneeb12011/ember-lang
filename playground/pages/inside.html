One loop, all the way down

Eight lines of Ember go in. Here is everything the compiler does to them on the way to machine code, using its real output, and what the runtime and the test suite do around it.

lexer.hpp, parser.hpp, modules.hpp

Text becomes a tree

The lexer cuts the file into tokens: fn, main, (, and so on. The parser, a hand-written recursive-descent parser, builds them into a syntax tree, using precedence climbing for operators. Bitwise operators bind tighter than comparisons, so x & 1 == 1 means what it looks like, unlike in C.

Then the module loader resolves imports. Each file is its own namespace, a file imported twice through different paths loads once, and an import cycle is an error.

sema.hpp, mono.hpp

Checked before anything runs

The type checker walks the tree and settles the type of every expression. It infers generic arguments from the call, and from what the surrounding code expects when the arguments aren't enough. It checks that every match covers every variant and that every path through a function returns.

ir.hpp

A tree becomes {{N0}} instructions

The checked program is lowered to IR: three-address code where every instruction does one thing to numbered virtual registers, r0, r1, as many as it needs. Labels like L0 mark the starts of basic blocks: straight runs of code that control flow can only enter at the top.

Here, r0 is total and r2 is the loop counter. The for loop has become a test at L0, a body at L1, an increment at L2 and a jump back. The lowering is deliberately naive: it copies freely and leaves the clean-up to the next stage.

opt.hpp

{{N0}} instructions become {{N1}}

The optimizer runs its passes until nothing changes. On this loop, four of them matter:

  • Constant propagation sees that r3 is always 10 and puts the 10 straight into the comparison.
  • Copy propagation sees that r1, the variable i, is only ever a copy of the counter r2, and uses r2 directly.
  • Coalescing writes the sum straight into r0 instead of into a temporary that is copied over afterwards.
  • Block cleanup merges the empty block L2 and removes the unreachable second ret.

Every pass must preserve runtime errors exactly: an optimization may never remove a division by zero or an out-of-bounds access that the unoptimized program would have hit.

After the optimizer: embc main.em --emit-ir

codegen.hpp

Virtual registers become real ones

The x86-64 back end gives each virtual register a real one with a linear-scan allocator. It computes how long each value lives from the control-flow graph and hands out eleven registers, spilling to the stack only when they run out.

Here nothing spills: total lives in rsi and the counter in rdi for the whole loop, so the loop never touches memory. The comparison and the branch fuse into cmp and jge, which jumps out when the counter reaches 10. Before the call, total moves into rdi, because that's where the System V calling convention puts the first argument. And since no value has to survive the call, no callee-saved register is used, so none has to be saved.

rt/ember_rt.c, 903 lines of C

A garbage collector that knows most objects die young

Structs, arrays and closures live on a heap managed by a generational collector. New objects are collected often and cheaply; objects that survive are promoted and checked rarely. A card-marking write barrier, emitted by the compiler on every pointer store, remembers where old objects point at new ones.

The collector doesn't move objects and scans the stack conservatively. That works because the register allocator guarantees every pointer that is live across a call sits in a callee-saved register or on the stack, where the collector looks.

tests/run_tests.py, tests/fuzz.py

Proving it, six ways

Every test program runs on the interpreter, as native x86-64 and as WebAssembly, each with the optimizer off and on. All six results must match the expected output exactly, and the expected output is computed by an independent Python program, never by Ember itself.

A fuzzer writes random valid programs and runs them on all six paths. When the paths disagree, a shrinker deletes lines until the smallest program that still disagrees is left. 1,000 programs, 1,000 agreements.

tests/bench

Measured, not guessed

Every optimizer change was kept or dropped on numbers. Wall-clock time on a shared machine varies by up to 30%, so the deciding number was the exact count of instructions executed, measured with cachegrind; paired timing runs settled the cases that count can't see, like a divide replaced by shifts.

Every pass can be switched off without rebuilding, so "with" and "without" always come from the same compiler binary.

wasm.hpp, playground/

And then, this website

Ember has a second back end that writes WebAssembly modules byte by byte. Separately, the compiler itself is plain C++, so it can be built for the browser: the playground and the tour run the real compiler, as a 900 KB WebAssembly file, inside a web worker that can be stopped if a program loops forever.

Its output was compared with the native compiler's on every test program: IR, assembly and error messages, 227 comparisons, all byte for byte identical.
